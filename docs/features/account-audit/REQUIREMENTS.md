# Application accounts, authorization, and database audit

- **Status:** Proposed
- **Date:** 2026-11-12

## Summary

SuperDBA must identify the application principal responsible for every authenticated Web request and every auditable database operation. Authentication, authorization, and audit attribution are server responsibilities. Browser-supplied history entries and database connection usernames are not substitutes for an application identity.

This feature introduces local application accounts, preserves authenticated reverse-proxy identities, carries the principal through the shared application layer, enforces per-principal access, and writes an append-only audit trail.

## Goals

- Identify the application principal that initiated a database operation.
- Support local username/password accounts and trusted reverse-proxy identities.
- Keep desktop mode local and backward compatible while assigning it an explicit local principal.
- Authorize access to connections and operation classes before application behavior runs.
- Record durable, server-generated audit events for database operations.
- Correlate application audit events with the database account used by the driver.
- Preserve the desktop/web transport boundary and shared application behavior.

## Non-goals

- Provisioning users or roles inside managed databases.
- Replacing database-native grants, roles, or audit logs.
- Sending passwords, session tokens, full result sets, or connection secrets to the audit log.
- Treating the existing query-history feature as a security audit trail.
- Adding multi-tenant data isolation to desktop mode.

## Identity model

Every application request has a `Principal` with these stable fields:

| Field | Meaning |
|---|---|
| `id` | Immutable internal identifier used by authorization and audit records |
| `subject` | Login name or proxy subject, unique within its authentication source |
| `display_name` | Optional presentation name |
| `source` | `local`, `proxy`, or `desktop` |
| `status` | `active` or `disabled` |

The internal identifier, not a mutable display name, is the audit identity. A Web session stores a snapshot of `principal_id` and resolves the current account status and grants for authorization-sensitive requests. Disabling an account invalidates its active sessions.

The trusted proxy must replace `X-SuperDBA-User`; SuperDBA validates it, maps it to a proxy principal, and stores that principal in the issued session. The header is removed before application dispatch. Password mode authenticates a named local account and no longer represents an anonymous shared user.

Desktop requests use a reserved local principal. Desktop attribution means “the local desktop application instance,” not a cryptographically verified operating-system user.

## Credential storage

- Local passwords are hashed with Argon2id using a unique salt and bounded parameters.
- Plaintext passwords are accepted only at account creation, password change, or login and are never persisted or logged.
- Account data is stored under the server data directory with restrictive filesystem permissions and atomic replacement.
- The first administrator is created through a one-time bootstrap flow. Startup must not create a known default password.
- Password changes and account disablement revoke existing sessions.

## Authorization model

Authorization has two layers:

1. A coarse capability level compatible with the existing `session`, `database`, `sensitive`, and `local-admin` command metadata.
2. Resource grants that restrict a principal to named connection IDs and allowed database operation classes.

The initial roles are:

| Role | Capability level | Database operations |
|---|---|---|
| `viewer` | `database` | Metadata and read-only SQL |
| `operator` | `database` | Read and data modification on granted connections |
| `administrator` | `local-admin` | Account administration and all explicitly enabled host capabilities |

SQL classification is defense in depth, not a replacement for database-native permissions. Each human operator should use an individual database account whenever the target database supports it.

Authorization is evaluated in the shared application layer. Desktop and Web transports must not implement divergent business policy. Transport checks may reject requests earlier but cannot be the only enforcement point.

## Audit model

Audit records are generated by the backend at the operation boundary and are append-only for ordinary application users. The minimum record is:

| Field | Meaning |
|---|---|
| `event_id` | Unique event identifier |
| `occurred_at` | UTC timestamp generated by the server |
| `principal_id` / `principal_subject` | Application actor snapshot |
| `session_id` / `request_id` | Request correlation identifiers |
| `action` | Stable operation name such as `query.execute` |
| `connection_id` | Saved connection used by the operation |
| `database_account` | Driver username when available |
| `database` / `schema` | Target scope when available |
| `statement_fingerprint` | Normalized hash used for correlation |
| `statement_preview` | Optional redacted, length-bounded preview |
| `outcome` | `started`, `succeeded`, `failed`, or `cancelled` |
| `duration_ms` | Server-observed execution duration |
| `rows_affected` | Count when available |
| `error_code` | Stable failure category without secret-bearing details |
| `client_address` | Web client address when derived through trusted proxy rules |

Full SQL text is disabled by default because statements can contain credentials and personal data. Deployments may opt into encrypted full-statement retention with an explicit retention period. Query results are never stored in the audit trail.

Audit writes must not be controlled by request payload fields. Failure to persist a mandatory audit record fails closed for mutating operations. Read-only operations may follow an explicitly configured availability policy, but the default is fail closed.

Audit exports require `sensitive`; retention changes and audit deletion require `local-admin` and produce their own audit events. Storage should support integrity verification through a hash chain or an external append-only sink.

## Request flow

1. The transport authenticates credentials and issues a session bound to a principal.
2. The transport constructs `ApplicationRequestContext` with the principal, session, request, deadline, and granted authorization level.
3. The application layer verifies account status, command capability, and connection grant.
4. The application layer emits an audit `started` record.
5. The database driver executes with the saved connection credentials.
6. The application layer emits the terminal audit outcome.

## Compatibility and migration

- Existing local Web bootstrap sessions map to a reserved bootstrap administrator only during migration.
- Existing remote shared-password deployments must create a named administrator before shared-password login is removed.
- Existing proxy deployments continue to send `X-SuperDBA-User`; the value becomes durable session identity.
- Existing saved connections remain unchanged. Their database username is recorded separately from the application principal.
- Existing query history remains a user convenience feature and is explicitly not migrated into the audit store.

## Delivery phases

### Phase 1: Principal propagation

- Add the principal type to the application layer.
- Preserve proxy subjects in Web sessions.
- Add reserved desktop and local-bootstrap principals.
- Include principal identifiers in structured Web audit events.

### Phase 2: Local accounts

- Add durable account storage and Argon2id password verification.
- Add one-time administrator bootstrap, login, logout, and session revocation.
- Add administrator account-management APIs and UI.

### Phase 3: Resource authorization

- Add role assignments and per-connection grants.
- Enforce shared application-layer policy for query, metadata, record, and administrative operations.
- Add read-only SQL classification as defense in depth.

### Phase 4: Durable database audit

- Add append-only audit storage and retention.
- Instrument query, batch, record, schema, import, export, and AI database operations.
- Add filtered audit review and export for authorized administrators.

## Acceptance criteria

- Two independently authenticated users produce distinguishable audit identities.
- A proxy-authenticated subject remains attached to the same issued session and appears in audit events.
- Password-authenticated sessions identify a named account; no shared anonymous password session remains after migration.
- Disabled accounts cannot create sessions and their existing sessions stop authorizing requests.
- A user without a connection grant receives a denial before connection credentials are resolved.
- Every SQL execution has correlated start and terminal audit records containing the application principal and database account when available.
- Audit records cannot be created, altered, or attributed by ordinary client payload fields.
- Secrets, session cookies, passwords, full query results, and database connection URIs never appear in audit output.
- Desktop and Web transports call the same authorization and audit services.
- `cargo check --no-default-features` and transport-boundary checks pass.

## Test strategy

- Unit tests for password hashing, subject validation, grants, SQL classification, redaction, and audit serialization.
- Application tests proving authorization occurs before credential resolution and driver execution.
- Web tests for named login, proxy identity persistence, session revocation, CSRF, and audit correlation.
- Desktop tests for the reserved local principal and shared application behavior.
- Integration tests using two principals and two database accounts.
- Negative tests proving headers and request bodies cannot forge the audit principal.

## Security considerations

- Account administration is a security-sensitive authorization change and is never classified as a beginner task.
- Proxy identity is trusted only when the deployment secret is valid and direct upstream access is blocked.
- Usernames are identifiers, not authorization evidence; grants are resolved server-side.
- Audit access itself can disclose sensitive operational metadata and requires explicit authorization.
- Application attribution complements database-native auditing. It cannot make a shared database account distinguishable inside the database server.
